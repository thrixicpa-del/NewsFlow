# Issue406 — повторное добавление тем после удаления производства

[Issue406](https://github.com/thrixicpa-del/NewsFlow/issues/406). Ветка `codex/production-topic-reset` от `43dd0709d7341eb79b308303031b5f3a47fd3ebc`; отдельный worktree. PR403/405 и main не изменялись. Frozen/EXE не собирались.

## Причина и исправление

Удаление производства уже очищало память заголовков, метаданные и списки тем. Защитные отметки удаления сохраняются намеренно: старые workers и аварийные копии не должны возвращать удалённый выпуск.

При ручном повторном добавлении заголовок получал новый ProductionItem ID, но не связанный ScenarioJob. Сохранение сессии рассматривало строку без Job как старую удалённую тему и отфильтровывало её. Пользователь не видел добавленную тему в UI. Проверка воспроизвела это и для темы без готового текста.

Повторное добавление теперь сохраняет ScenarioJob с новым ID до записи сессии. Путь ручного ввода использует ту же защиту, что передача идей в сценарии. Старые отметки удаления остаются действующими, новая тема с новым ID видна после перезапуска. Повторные строки внутри одного пакета, включая другой регистр, и уже добавленные темы не создают дубли.

Дополнительная проверка UI выявила, что reset не записывал ID темы, если ScenarioJob ещё не существовал. Теперь при удалении учитываются ID из ProductionItems и текущего контекста тем, а также Jobs. Поздняя задача со старым ID не возвращает удалённый выпуск. Это не стирание всех защитных отметок, а корректное разделение старой и заново добавленной темы.

Windows-native также выявил соседний дефект очистки staging позднего worker: исходный путь родителя сравнивался с canonical границей. При junction/алиасе Windows эти пути различаются, и удаление пустых папок могло подняться до рабочего output root. Новый тест через disposable junction сначала воспроизвёл потерю root (RED); обход теперь использует canonical родителей (GREEN). Assertions о сохранении пустых рабочих папок не ослаблялись. Дополнительный независимый review замечаний не нашёл; alias-регрессия PASS, с отдельным FAIL production hash guard при открытом рабочем NewsFlow.

Используется прежняя кнопка и контрольная фраза. Переиспользуемые направления, каналы, OAuth, настройки, библиотеки и модели сохраняются. Автотесты работают с disposable-профилями, без удаления рабочего производства пользователя.

## Ограничения и сохранённые FAIL

Рабочий NewsFlow запущен. Пользователь сообщил, что пока не может закрыть его. Несколько локальных canonical-прогонов обнаружили изменение хэша реального settings.json и завершились `PRODUCTION_WRITE_GUARD=FAIL`, несмотря на успешные функциональные assertions. Причину записи этот монитор не устанавливает; работающий экземпляр может писать параллельно. Поэтому локальная проверка неизменности рабочего профиля **BLOCKED**, а не GREEN. Guard не отключался и не перенаправлялся на фиктивный профиль. Рабочее приложение не завершалось; очистка в нём не запускалась. Все вызовы удаления в тестах выполнялись с `NEWSFLOW_TEST_MODE=1`, отдельными NEWSFLOW_TEST_ROOT/LOCALAPPDATA и тестовыми производственными каталогами. Прежние FAIL сохранены в игнорируемых логах `.superpowers/production-topic-reset/`.

Отдельный read-only монитор прочитал хэш и mtime рабочего settings.json 16 раз за 15 секунд, когда автоматические тесты не выполнялись: хэш менялся. Это подтверждает параллельные изменения вне тестового прогона, но не устанавливает автора каждой прежней записи и не снимает предыдущие FAIL.

Первый baseline имел WinError216 из-за LFS pointer вместо FFmpeg. Для тестовых видео материализован уже существующий cached FFmpeg после совпадения SHA256 с HEAD; это не сборка EXE. Перед коммитом исходный LFS pointer восстановлен.

Frozen lock не обновлялся без соответствующего Frozen build. Docker NOT RUN: Linux engine pipe недоступен. Packaged/clean Windows/release smoke NOT RUN по границам задачи. Выпуск не объявляется release-ready; main/merge/закрытие issue не выполняются.
