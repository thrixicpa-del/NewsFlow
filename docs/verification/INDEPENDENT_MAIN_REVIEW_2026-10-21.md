## Подтверждённые дефекты и исправления

### 1. Выход за выбранный интервал и накопление лишних кадров

GPU command builder запрашивал `duration + 1/30 + 0.002` для каждой сцены.
Выход отдельной сцены не ограничивался её кадровым бюджетом; хвост проекта
мог расширяться ещё на 0.15 секунды. Такие дополнительные исходные кадры
лежали за проверенным visual-evidence интервалом.

**RED:** настоящий FFmpeg для трёх сцен по секунде выдавал 96 кадров / 3.2
секунды вместо 90. Источник был красным на `[0, 1)` и синим после секунды;
синие кадры появлялись в результате с включённым и выключенным zoom.

**Исправлено:** точное исходное окно, явный `trim=end_frame`, общий расчёт
кадров по накопленным границам проекта и передача этого расчёта через
границы GPU chunks. Непроверенное расширение хвоста удалено. Существующая
проверка достаточной длины видео относительно озвучки сохранена.

**GREEN:** 90 кадров без синего участка; четыре сцены по 0.45 секунды дают
54 кадра при размерах chunk 1 и 3, с непрерывными PTS и звуком в конце.
Независимая дополнительная матрица из 125 комбинаций FPS, source_start и
длительности также дала ожидаемое число декодированных кадров.

**Дополнение по настоящему Windows CI:** первый запуск новых регрессий
обнаружил отличие FFmpeg: на границах chunks терялся кадр или нарушался PTS.
Это не списано на тестовую среду. Независимое воспроизведение на imageio
FFmpeg 7.0.2 показало, что после concat автоматический output fps становился
25 вместо 30; при chunks 1 и 3 получалось соответственно 48 и 47 кадров.
В command builder явно заданы `-r 30 -fps_mode cfr`. На FFmpeg 6.1.1 и
7.0.2 реальные кадры, PTS, цвета и аудио проходят прежние строгие проверки;
для дробного примера снова получается 54 кадра / 1.8 секунды. В постоянный
набор добавлен отдельный прогон с bundled imageio runtime, чтобы Linux CI
проверял не только системный бинарник. Проверки не ослаблены.

### 2. Независимое округление сцен в Remotion manifest

**RED:** четыре сцены по 0.45 секунды превращались в 56 кадров вместо 54.

**Исправлено:** Remotion manifest использует ту же накопленную кадровую
сетку. Длительности примера теперь `[14, 13, 14, 13]`, начала
`[0, 14, 27, 41]`. Дробный конец озвучки учитывается округлением вверх.
Это проверка manifest; полноценный Chromium render в этой локальной среде
ограничен отсутствующим браузером, см. ниже.

### 3. Читаемый, но укороченный исходник считался пригодным

Проверки сохранённого проекта принимали любой читаемый файл длиннее
0.05 секунды. Для современных проектов с `source_policy` отдельный legacy
путь исправления хвоста уже не применялся.

**RED:** файл длиной 1 секунда принимался для двухсекундной сцены; файл
длиной 3 секунды принимался при `source_start=2`, `duration=2`.

**Исправлено:** preflight и recovery проверяют весь оставшийся сохранённый
интервал. Continuity также учитывает требуемую длину сцены. Замена
сохраняет длительность и VoiceMap segment IDs; при исчерпании замен
применяется предусмотренный continuity fallback. Legacy-проекты сохраняют
свой существующий маршрут восстановления.

### 4. Автоматические фильтры повторно отклоняли ручной блок

Подготовка вручную выбранного блока учитывала ручной выбор, но preflight
и recovery вновь применяли автоматические ограничения story/страны.

**RED:** выбранный пользователем `Iran_port.mp4` из сохранённой папки
блока отклонялся или не принимался как замена.

**Исправлено:** допустимость ручного блока определяется каноническим
сохранённым корнем папки. Подстановка файла вне этого корня отклоняется.
Автоматические источники сохраняют семантические ограничения. Проверены
выбор внутри блока, отказ для внешнего файла и сохранение voice beat.

### 5. Явная Pause/Continue терялась при конкурентной записи

Merge настроек сохранял свежие значения диска для полей, совпадающих с
загруженным снимком. Однако повторный явный выбор пользователя тоже мог
совпасть с этим снимком и потеряться после противоположной записи другого
процесса.

**RED:** обе последовательности Pause/Continue воспроизведены на реальном
временном settings.json.

**Исправлено:** явная команда помечает принадлежащее ей поле; merge под
существующим mutex применяет явный выбор. Пометка очищается после
успешной записи. Последующая фоновая запись старого объекта не отменяет
более новое решение пользователя.

### 6. Сохранение шаблона и диапазонов имело ту же гонку

**RED:** повторное явное сохранение активного шаблона, template preset
или range preset теряло введённые поля. Дополнительно частичное изменение
только min/max могло пройти предварительную проверку, а после merge
образовать `minimum > maximum`.

**Исправлено:** `save_template` владеет шаблоном и только присутствующими
в payload полями длины; ranges принадлежат команде только при переданном
списке. Template preset сохраняет свой существующий полный контракт
активных полей, range preset владеет активными ranges. Коллекции пресетов
не помечаются целиком. Границы длины повторно проверяются после merge под
mutex; противоречивое изменение отклоняется до записи settings и backup.
Ноль сохраняет значение «не задано».

Проверены omitted fields, сохранение параллельно добавленного пресета,
одноразовое владение, обе конфликтующие границы и неизменность файла и
backup при ошибке.

### 7. Ожидание или скачивание MP3 отображалось как READY

Task Center находил слово «готов» в сообщениях «Ожидаем готовый MP3» и
«Скачиваем готовый MP3» и преждевременно показывал завершение.

**RED:** реальные строки провайдеров воспроизвели неправильный статус.

**Исправлено:** эти узкие формулировки дают WAITING/RUNNING. Явные
`jobState` и `voiceError` сохраняют приоритет; старый MP3 в `path` не
превращает новое ожидание в успешное завершение.

### 8. Два процесса могли одновременно владеть генерацией обложек

PID-файл становился видимым до завершения JSON-записи; конкурентный
процесс мог счесть его пустым/устаревшим и перехватить. При восстановлении
устаревшего lock существовало аналогичное окно. Windows source process
дополнительно проверялся как будто это всегда `NewsFlowCore.exe`.

**RED:** два отдельных spawned-процесса одновременно получали владение
в обоих контролируемых межпроцессных порядках выполнения.

**Исправлено:** read/reclaim/publication и release сериализуются
стабильным OS lock. Проверка PID учитывает текущий source/Frozen runtime.
Проверены частичная публикация, stale replacement, отказ публикации,
последующее восстановление и запрет снятия чужого lock. Это устраняет
подтверждённый путь дублирования batch-запусков.

### 9. Локальный Remotion server открывал файлы вне проекта

HTTP endpoint декодировал присланный путь и читал файл без проверки его
принадлежности manifest. Клиент, способный обратиться к этому локальному
серверу во время рендера, мог запросить посторонний файл.

**RED:** реальный HTTP-запрос вернул временный файл вне manifest с 200,
а его диапазон байтов — с 206. Проверка использовала только специально
созданный тестовый файл.

**Исправлено:** сервер получает allowlist путей текущего manifest,
нормализует их и закрепляет resolved target. Посторонний путь, обход через
нормализацию и замена выбранного файла ссылкой на посторонний отклоняются.
Разрешённое media чтение и Range сохраняются. Helper включён в
`asarUnpack` рядом с renderer; зависимости и lockfile не менялись.

Дополнительная независимая проверка подтвердила старые ошибки Range:
`bytes=0-0` возвращал весь файл, `bytes=-3` — первые четыре байта, а
диапазон за концом файла ошибочно давал 206. Исправлен узкий parser:
single-byte, suffix и open-ended ranges возвращают правильные данные;
невыполнимые диапазоны и диапазон пустого файла дают 416 с `bytes */size`.
Все случаи проверяются настоящими HTTP-запросами.
