# Footage V3 — отчёт для проверки владельцем

Статус: исходниковая реализация на отдельной ветке; **не production/release-ready**. `main` не изменён. Issue: [#402](https://github.com/thrixicpa-del/NewsFlow/issues/402). BASE_SHA: `43dd0709d7341eb79b308303031b5f3a47fd3ebc`. Ветка: `codex/footage-semantic-person-fallback-v3`.

## Причины и изменения

Воспроизведены RED-регрессиями: совпадения подстрок «Армения/армия», «танкер/танк», переносный/отменённый удар, урожай/протест, протекание заголовка и прошлой персоны; старый запрос VoiceMap при смене темы; отсутствие выбранных корней в retrieval; отключённые/изменённые файлы в финальном inventory; массовое удаление строк при пропаже родительского каталога; повторная подготовка метаданных и текстовых векторов; уничтожение корпуса после `mark_used`/оценки; гонка чтения статистики и удаления; подмена человека, потеря подтверждённого интервала при reuse/ротации/восстановлении/достройке хвоста; сохранение старого подтверждения после замены файла.

Финальный topic-agnostic fallback действительно обходил смысловую пригодность. Теперь активные вызовы сохраняют локальный запрос, требуют положительный контекст и ограничения; расширенный retrieval использует контекст текущей сцены и score floor. Если материала нет, сохраняется `.newsflow.partial` с причиной и номером сцены; это не готовый проект и не полный MP4.

Новый лёгкий `scene_intent.py` нормализует алиасы/роль говорящего, отделяет локальное действие от общего заголовка, разрешает только близкие однозначные местоимения. Не вызывается API на сцену. Уточнения охватывают и отрицание отмены, фактический обстрел несмотря на перемирие, поезд/поездку, НПЗ и серверы. Это ограниченные локальные правила, а не обещание полного понимания русского языка.

Корпус хранит подготовленные метаданные и postings. NumPy обрабатывает совпадения по позициям вместо Python-цикла «каждый запрос × каждый клип». LRU текстовых векторов ограничен 512 запросами на индекс; общий корпус — четырьмя базами. Изменение использования/оценки обновляет статистику без перечитывания матрицы. SQLite-триггеры фиксируют изменения других процессов; чтение ревизий/статистики идёт в одном snapshot. Content epochs и файловая подпись учитывают восстановление/замену БД. Проверка подписи выбранных файлов не разрешает использовать старый embedding после изменения исходника.

## Активный маршрут и совместимость

`Editor → run-montage-queue → preload IPC → Electron main/startMontageQueue → python -m scriptor.bridge run-montage-queue → prepare_montage → VoiceMap/local planner → search_many → selector/reuse/context → TimelineProject → existing render_project`.

Проверен реальный source Electron, а не вызов одной Python-функции. В нём отсутствующая точная персона получает тематический контекст, следующая сцена переключается на танкер, очередь создаёт MP4; проект переживает перезагрузку страницы без перемешивания. Нативный выбор каталога/файла не автоматизировался: фикстуры и настройки подготовлены в тестовом профиле. Полный restart приложения, живые провайдеры, GPU и ручная приёмка настоящих роликов этим не доказаны.

Существующие шестисекундные биты, остаток, движки, настройки, source families, резервации и history сохранены. Ограничение длительности подтверждённого окна действует также при восстановлении хвоста. Старые `.newsflow` читаются; `selection_diagnostics` необязательно. Generic `FootageItem` и legacy JSON не менялись: разметка принадлежит `IndexedFootageItem`. В SQLite добавляются необязательная колонка разметки и revision-триггеры. Рабочая пользовательская БД этим запуском не обновлялась.

## Люди и fallback

**PERSON_MATCH=NOT VERIFIED на реальных видео.** Алиасы — расширяемый словарь, не распознавание лица. Подтверждением считаются только явно переданные `manual/curated` интервалы, привязанные к размеру/mtime файла; имя/папка/CLIP-score не дают confirmed. Проверены контрактные положительные/отрицательные случаи, совместные кадры, поздние интервалы, частичное противоречие, ошибочная фамилия в имени файла и обновление данных. Никакие кадры не отправлялись наружу; новая модель распознавания не добавлялась. Разметка доступна через локальный API индекса `set_person_evidence`, отдельный новый экран не создавался.

Отсутствующее лицо не является ошибкой само по себе. Для неподтверждённого контекста сохраняются отдельный person-status и существующий уровень fallback; `STRICT_MATCH` не выдаёт неизвестное лицо за точное совпадение. Совпадение человека не означает подтверждённую съёмку описанного события.

**TOPICAL_FALLBACK: контрактные/metadata проверки PASS; визуальная приёмка NOT VERIFIED.** На инженерных видео проверяется прохождение полного pipeline, а не содержание изображения. Настоящих независимо размеченных видео с людьми, дипломатией, танкерами, кибер/сельхоз-темой в разрешённом тестовом наборе не было. Пользовательские оригиналы для этого не копировались и не публиковались. Цвет/движущийся паттерн и корректная метка не засчитываются как визуальная точность.

## Разнообразие

**DIVERSITY_REGRESSION=PASS на фиксированном suitable-pool сравнении; реальная библиотека NOT VERIFIED.** Сравнивались BASE и AFTER: 32 ролика × 24 сцены, normal/fast, serial/parallel, достаточный пул/дефицит. Начальная история восстанавливалась между режимами, внутри серии сохранялась. Весь агрегированный JSON совпал.

| Условия | Разные клипы BASE → AFTER | Разные семьи | Соседние повторы | Одинаковые начала между роликами |
|---|---|---|---|---|
| Достаточно, normal, serial/parallel | 24 → 24 в каждом ролике | сохранены | 0 → 0 | 0 → 0 |
| Достаточно, fast 50%, serial/parallel | 12 → 12 в каждом ролике | сохранены | 0 → 0 | 0 → 0 |
| Дефицит, normal/fast, serial/parallel | 5/4/4/4 → 5/4/4/4 | сохранены | совпадают | 3 → 3 |

Тройки повторов, пересечения наборов и показатели семей доступны в JSON. Дефицит специально не считается успехом уникальности. Процент fast reuse по-прежнему означает длительность начального участка с подготовкой нового пула, минимум два бита, затем reuse готовых proxy-окон и semantic escape при смене темы. Диагностическая доля разных путей не переопределяет настройку пользователя.

## Измерения retrieval

Windows, Python 3.12.10, Node 24.19.0, фактический pnpm 11.25.0; lockfile не менялся. Одинаковые 512-мерные синтетические векторы/seed, 1 разрешённый корень, 12/72 различных запросов, limit=32, пять повторов. Существование/подпись файлов замокированы только в этом микробенчмарке. Text embedder детерминированный тестовый; загрузка CLIP/декодирование/диск не измеряются. Трассировка памяти отключена во время замера latency.

| Записи / запросы | Warm BASE, ms median [min–max] | Warm AFTER | После usage BASE → AFTER, ms |
|---|---|---|---|
| 1k / 12 | 15.19 [13.87–28.84] | 7.18 [6.37–7.57] | 29.75 → 10.75 |
| 1k / 72 | 51.05 [40.73–58.85] | 18.43 [15.51–27.89] | 66.23 → 20.85 |
| 10k / 12 | 137.34 [117.74–177.21] | 20.53 [18.44–25.17] | 280.48 → 83.94 |
| 10k / 72 | 409.62 [388.36–488.93] | 58.60 [38.18–80.34] | 554.71 → 103.25 |
| 20k / 12 | 284.29 [260.05–326.56] | 25.90 [25.11–65.50] | 586.41 → 135.18 |
| 20k / 72 | 772.90 [723.39–803.20] | 76.36 [71.95–80.90] | 1060.48 → 161.12 |

Цена: холодная подготовка корпуса стала тяжелее (20k/72: 299.60 → 443.11 ms), Python allocation peak для первоначального 20k-корпуса вырос 106.98 → 129.91 MiB. Нулевые значения памяти в строках 72 запросов означают уже загруженный корпус, не нулевое потребление. Это tracemalloc allocation peak, не полный RSS/VRAM. Cold в JSON — корпус подготовлен отдельно, текстовый кеш холодный только на первом повторе; повторный отдельный процесс/полный холодный запуск моделей не оценён.

**Ускорение полного пользовательского процесса НЕ ДОКАЗАНО.** Четыре небольших инженерных ролика показали замедление подготовки/рендера; ранние замеры также имели конкуренцию с регрессиями. Последующее последовательное сравнение с отдельными render/proxy-кешами сохранено отдельно. Нельзя переносить ускорение retrieval на весь экспорт или объявлять критерий скорости выполненным. Полный RSS, реальная библиотека 20k и стоимость настоящей проверки людей остаются непроверенными.
