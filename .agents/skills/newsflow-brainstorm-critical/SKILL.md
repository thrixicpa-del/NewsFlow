# NewsFlow Brainstorm + Critical Thinking

Используй этот skill, когда нужно придумать новую функцию, переосмыслить workflow, выбрать архитектурный подход или найти нетривиальный способ упростить NewsFlow. Не используй его как обязательный ритуал для уже воспроизведённого мелкого бага.

## Режимы

1. **Frame** — сформулируй реальную проблему пользователя, ограничения и критерий успеха.
2. **Diverge** — создай 4–7 действительно разных подходов: минимальный, эволюционный, радикальный, автоматизированный, ручной/гибридный; при необходимости один «неочевидный» вариант.
3. **Challenge** — для каждого сильного варианта выпиши, почему он может оказаться плохим: сложность, UX, данные, стоимость, provider limits, latency, поддержка, migration, safety.
4. **Converge** — не делай абстрактный рейтинг. Выбери подход только если пользователь просит техническую рекомендацию; объясни trade-offs и условия, при которых решение нужно пересмотреть.
5. **Experiment** — определи минимальный эксперимент, измеримый критерий и stop condition.

## Анти-паттерны

- Не предлагай переписывание системы только потому, что оно эстетичнее.
- Не считай больше настроек автоматически большей гибкостью.
- Не добавляй идею в активный Goal без согласования.
- Не используй «AI» как ответ без описания данных, контроля ошибок, стоимости и fallback.
- Не принимай текущий UI/архитектуру как неизменную истину, но и не ломай подтверждённые production-контракты ради концепта.

## Формат результата

Дай: проблема → варианты → сильные возражения → рекомендуемый эксперимент → критерий успеха → что не делать сейчас.

## Общие границы NewsFlow

- Skill — это методика, а не разрешение на внешние или опасные действия. Следуй текущей задаче пользователя, подтверждённым правилам репозитория и доступным инструментам.
- Перед изменением кода подтверждай репозиторий, ветку, SHA, рабочее дерево, версии и фактический runtime. Не считай старый чат текущим состоянием.
- Не трогай оригинальную production-медиатеку, реальные ключи, OAuth, рабочие очереди и пользовательские данные в автоматических тестах. Используй синтетические фикстуры или отдельно согласованные копии.
- Не делай merge в `main`, force-push, публикацию, платный provider-call, массовое обновление зависимостей или расширение прав без явного разрешения.
- Быстрый цикл по умолчанию: source/DEV → targeted tests → relevant regression → integration/E2E при необходимости → commit. Полный EXE/TEST RC — на контрольной точке или при packaging-specific дефекте.
- Факт отделяй от гипотезы. Не называй тест выполненным, пока он не был реально запущен; SKIP не равен PASS.
- Не маскируй сбой отключением теста, `continue-on-error`, удалением проверки или возвратом фиктивного success.
- Исправляй первопричину минимальным изменением; широкую перестройку выноси в отдельное решение.
- Для каждого результата фиксируй: expected/actual, root cause evidence, изменённые файлы, SHA, команды, PASS/FAIL/SKIP/BLOCKED и оставшиеся риски.
